# Mac App Store submission

The App Store build is a **different product** from the direct download, and
deliberately so. Decide whether that trade is worth making before starting.

## What the sandbox costs

App Store apps must be sandboxed. This was tested rather than assumed — the
bundle was re-signed with `com.apple.security.app-sandbox` and run:

| Capability | Sandboxed | Consequence |
|---|---|---|
| `AppleSmartBattery` via IOKit | **works** | Full readings: watts, rail, current, flow, health |
| Process attribution via `/bin/ps` | **blocked** | Cannot name the app draining your battery |
| SMC charge limit | **impossible** | Needs a privileged helper, which the store forbids |

So the store edition monitors correctly but cannot tell you that oMLX is what
your charger is losing to, and can never carry a charge limit.

`ProcessWatch` is compiled out under `-DAPPSTORE` rather than left to fail
silently, and the panel hides itself when there is nothing to show.

## One-time setup

### 1. Apple Distribution certificate

**A Developer ID Application certificate cannot be used for the App Store.**
They are different types, and this is the usual first stumble.

Xcode → Settings → Accounts → your Apple ID → Manage Certificates → **+** →
**Apple Distribution**.

While there, also create **3rd Party Mac Developer Installer** — required to
sign the installer package.

```bash
security find-identity -v -p codesigning
```

You want both `Apple Distribution: …` and `3rd Party Mac Developer Installer: …`.

### 2. App ID and provisioning profile

At [developer.apple.com](https://developer.apple.com/account/resources):

1. **Identifiers** → register `com.bluehawana.smartcharging` (must match
   `CFBundleIdentifier` in `Resources/Info.plist`)
2. **Profiles** → new **Mac App Store** profile for that identifier
3. Download it and save as `Resources/embedded.provisionprofile`

That path is gitignored; the profile is account-specific and does not belong
in the repository.

### 3. App Store Connect record

At [appstoreconnect.apple.com](https://appstoreconnect.apple.com) → Apps → **+**

| Field | Value |
|---|---|
| Platform | macOS |
| Bundle ID | `com.bluehawana.smartcharging` |
| Category | Utilities |
| Age rating | 4+ |
| Price | Free |

**Privacy nutrition label:** *Data Not Collected*. This is accurate — the app
reads a local sensor, makes no network requests, and stores its history in
`~/Library/Application Support/SmartCharging` on the user's own machine.

**Screenshots:** 2880×1800, generated by `swift Tools/makeshots.swift`. Use
`screenshots-ready.json` for the verified set.

## Building and uploading

```bash
make appstore-check      # verifies certificate and profile
make appstore VERSION=1.0.0
```

Then upload:

```bash
xcrun altool --upload-app -f build/SmartCharging-1.0.0.pkg -t macos \
  --apple-id <app-store-connect-app-id> \
  --keychain-profile smartcharging-notary
```

Review typically takes one to three days. First submissions are commonly
rejected once; read the resolution centre message rather than resubmitting
unchanged.

## Likely review questions

**Why does it read battery hardware?** It reports charging status to the user.
IOKit registry reads are permitted under the sandbox and no entitlement beyond
the sandbox itself is requested.

**Does it duplicate system functionality?** macOS shows charging *state*, not
delivered wattage, negotiated voltage or the cable's current ceiling. Those are
not surfaced anywhere in the system UI.

**Menu-bar-only behaviour.** The app opens a window on first launch and can be
reopened from the menu bar item, so it is not a background-only agent.

## Keeping both editions

The direct build stays the complete product — process attribution now, charge
limiting later. The store edition exists for discovery: people search "battery"
in the App Store and find nothing like this.

If only one is maintained, keep the direct build. It is the one that can carry
the features worth paying for.
